# 技術仕様書

## 1. テクノロジースタック

初めてのWeb開発であること、GitHub Pagesでの静的公開を前提としていることから、
ビルドツールを使わない「プレーンJS/HTML/CSS」構成とし、できるだけシンプルに保つ。

| 種別 | 採用技術 | 理由 |
|---|---|---|
| マークアップ | HTML5 | 標準技術。特別な理由がない限りシンプルな構成にする |
| スタイル | CSS3(素のCSS) | ビルドツール不要。フレームワークは導入しない |
| ロジック | JavaScript(ES2020以降、モダンブラウザのネイティブ機能のみ) | トランスパイル不要。`<script type="module">` でファイル分割 |
| 型付け | JSDocによる型注釈 | トランスパイル不要のまま型チェックを行うため |
| 地図表示 | Leaflet(CDN読み込み) | 軽量・APIキー不要・タイルレイヤーの切り替えが容易 |
| 地図タイル | 国土地理院タイル | APIキー不要、標高データとの一貫性、日本国内特化で見やすい |
| 標高取得 | 国土地理院 DEMタイル(PNG) | APIキー不要、CORS対応。タイル単位で取得するため、補間点が多くてもリクエスト数を抑えられる |
| グラフ描画 | Chart.js(CDN読み込み) | 軽量でドキュメントが豊富、折れ線グラフの色分けが容易 |
| GPXパース(次期) | 標準のDOMParser(XMLとして解析) | 追加ライブラリ不要 |
| リント | ESLint | コードの誤り・規約違反の検出 |
| 型チェック | TypeScript(`tsc --noEmit` + `checkJs`) | JSDocの型注釈をもとにJSファイルを型チェックする(JSは生成しない) |
| ホスティング | GitHub Pages | 無料の静的ホスティング、リポジトリと直結 |
| バージョン管理 | Git / GitHub | ソース管理・公開の両方を兼ねる |

**方針:**
- 実行時にはビルドツール(Vite等)やフレームワーク(React等)を使わない。
  ライブラリはすべてCDN経由の `<script>` タグで読み込み、`git push` するだけで
  GitHub Pagesに反映される状態を保つ
- npmは**開発時のリント・型チェック用ツール(devDependencies)の管理のみ**に使う。
  公開されるアプリはnpmパッケージに依存せず、`node_modules` はコミットしない
- CDNから読み込むライブラリはバージョンを固定し、`integrity`(SRI)属性を付与する

## 2. 開発ツールと手法

- エディタ: 制約なし(VS Code等、任意)
- バージョン管理: Git(GitHubリポジトリ)
- デプロイ方法: GitHub Pages(`main` ブランチのリポジトリルートを公開元に設定。
  詳細は `repository-structure.md` を参照)
- ローカル確認: 簡易HTTPサーバー(`npx serve .`、またはVS Codeの「Live Server」拡張機能)を利用する。
  ES Modulesは `file://` では読み込めないため、`index.html` を直接開く方法は使わない
  (本devcontainerには最小構成のPythonのみが入っており `python3 -m http.server` は使えないため、
  Node標準で使える `npx serve` を基本とする)
- リント: `npm run lint`(ESLint)
- 型チェック: `npm run typecheck`(`tsc --noEmit`)
- コード変更後は必ずリント・型チェックを実施し、エラーがない状態でコミットする
- テスト: 自動テストは本フェーズでは導入せず、手動での動作確認を基本とする
  (将来的に必要になれば `development-guidelines.md` で追記検討)
- ブラウザでの動作確認補助: devcontainerにはPlaywright用のChromium依存パッケージを導入している。
  これはClaude Codeがブラウザを操作して画面の動作確認・スクリーンショット取得を行うためのもので、
  正式な自動テスト(E2Eテスト)としては位置づけない。E2Eテストが必要になった時点で導入を検討する

## 3. 技術的制約と要件

- **サーバーサイドを持たない**: GitHub Pagesの静的ホスティングのみで完結させる
- **APIキー不要な外部サービスのみ利用**: 国土地理院の地図タイル・DEMタイルはAPIキー不要で
  CORSにも対応しているため、フロントエンドのJavaScriptから直接取得できる
- **対応エリアは日本国内限定**: 国土地理院データの提供範囲に依存する
- **出典表示の義務**: 地図タイル・標高データともに国土地理院のクレジット表示が必要
  (画面のフッターに明記する)
- **DEMタイルのデコード**: 画像を `crossOrigin = "anonymous"` で読み込み、canvasの `getImageData` で
  ピクセル値を取得する。タイル仕様・標高の算出式は `functional-design.md` の「API設計」を参照
- **ブラウザ対応**: 最新版のChrome / Safari / Firefox / Edgeを対象とし、
  古いブラウザ(IE等)は対象外とする

## 4. パフォーマンス要件

- **区間補間とタイル取得量**: 経由地点間をサンプリング間隔50mで補間するため、
  100kmのルートでは約2,000点となる。標高はタイル単位で取得するため、リクエスト数は点数ではなく
  ルートが通過するタイル数(10mタイルで1枚あたり約2km四方)に比例し、100kmでも数十〜百枚程度に収まる
- **タイルのキャッシュ**: 取得済みタイルはメモリ上にキャッシュし、同じタイルへの再リクエストを行わない
- **差分更新**: 経由地点の追加時は、追加された区間のみ補間・標高取得を行う
- **同時リクエスト数の制限**: タイルの同時取得数に上限(例: 6件)を設け、国土地理院サーバーへの負荷を抑える
- (次期)GPX読み込み時も、トラックポイントを経由地点として扱い同じ間隔で再サンプリングするため、
  ポイント数が多くても処理量は距離に比例する
- 地図操作(パン・ズーム・クリック)がもたつかないよう、地図上の描画要素(マーカー・線)は
  必要最小限に留める。補間点は地図上に描画しない
- 断面図の再描画はルート変更のたびに行う。点数が多い場合はChart.jsの間引き(decimation)機能を利用する
